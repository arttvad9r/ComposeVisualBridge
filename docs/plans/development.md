## 1. Сделать редактор надёжным — R3–R7, R11

- [ ] Зафиксировать воспроизводимые браузерные сценарии до изменений: маленький viewport, вложенные/перекрывающиеся элементы, край/центр контейнера, отмена drag, перенос из дерева и в дерево, прокрутка, Undo/Redo после resize, сохранение раскрытия при правке.
- [ ] Выбрать минимальный инструмент автоматизации браузерных проверок как dev-зависимость; runtime оставить без зависимостей. Не вводить новый frontend-фреймворк ради тестов.
- [ ] Исправить найденные ошибки событий указателя, выбора, фокуса и индикаторов. Проверить режим точного размера, пустое значение, 0, дробные значения, неверный ввод и границы.
- [ ] Проверить клавиатурные альтернативы и читаемость подписей в узкой панели. Сохранить русские пользовательские подписи.

Проверка: `npm test`, синтаксическая проверка модулей и новая команда браузерных тестов, добавленная выбранным инструментом. Каждая операция даёт ожидаемое дерево/diff, Undo возвращает точный исходный документ; незавершённый drag ничего не меняет.

## 2. Прояснить передачу и восстановление — R7, R8, R12

Зависит от этапа 1 для стабильных UI-проверок.

- [ ] Отобразить ID/ревизию последнего снимка, отличие current от applied и понятный следующий шаг. Явно объяснить, что кнопка не запускает агента.
- [ ] Добавить явный тестовый режим передачи: пометка сохраняется в снимке и видна агенту. До реализации действует поручение пользователя и AGENT.md; сам снимок не даёт разрешения на изменение кода.
- [ ] До изменения схемы описать совместимость со schemaVersion 1 и миграцию старых сессий. Не менять смысл existing revision/sourceRevision.
- [ ] Покрыть тестами быстрый ввод и Apply, отказ диска, конфликт двух окон, перезапуск, импорт поверх черновика и сохранность старого applied.

Проверка: UI однозначно показывает черновик/переданный снимок; тестовая передача распознаётся агентом; после каждой ошибки пользователь может экспортировать работу, а последний успешный снимок остаётся читаемым.

## 3. Проверить цикл с настоящим проектом — R1, R2, R9

Зависит от этапа 2. Для записи в целевой проект нужно отдельное поручение на реальный перенос.

- [ ] Выбрать один экран и реальное состояние/размер устройства. Получить baseline и скриншот, проверить ссылки source и хеши исходников.
- [ ] Выполнить разрешённый перенос небольшой отправленной правки: текстовое выравнивание, размер или порядок. Сохранить callbacks и общие компоненты в согласованном объёме.
- [ ] Проверить изменение кода между созданием baseline и переносом: агент должен обнаружить конфликт и не применять старый снимок вслепую.
- [ ] Собрать целевой проект его штатной командой, проверить реальный Android-экран, подготовить новый baseline из изменённых исходников.

Проверка: конкретные команды сборки берутся из выбранного репозитория; скриншот соответствует согласованному изменению. Отсутствие устройства/Preview отмечается как незавершённая визуальная проверка, а не успех.

## 4. Подготовить интеграцию Codex/Claude — R10

Можно проектировать после этапа 2; завершение зависит от подтверждённого цикла этапа 3.

- [ ] Проверить доступный механизм интеграции каждой оболочки по актуальной документации. Выбрать skill-пакеты или MCP на основании необходимых возможностей; браузерный UI и файловый контракт оставить общими.
- [ ] Подготовить команды «создать макет», «открыть редактор», «прочитать переданный снимок» с понятными ошибками и без автоматического применения тестового черновика.
- [ ] Описать установку, удаление, расположение данных и запуск; установку глобально выполнять только по запросу пользователя.
- [ ] Проверить одинаковый макет в Codex и Claude; отдельно проверить localhost во встроенных браузерах.

Проверка: в каждой выбранной оболочке агент открывает редактор и читает тот же applied; различия оболочек не меняют JSON-протокол. Непроверенную оболочку не объявлять поддержанной.
