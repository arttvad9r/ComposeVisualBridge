# Нативная проверка размеров и отступов — 11 октября 2026

Рабочая версия 0.8.1 после исправлений A4/A5. Выполнены импорт и две последовательные итерации: браузерная правка → тестовый снимок → Kotlin-план → запись в отдельную копию → debug-сборка → настоящий Android-кадр → повторный импорт.

**Нативный перенос сохраняет порядок модификаторов и правильно заменяет отступы по осям. Визуальное соответствие браузера и Android не принято: обнаружены расхождения размеров и заливки.** Это проверка конкретной статической сцены, а не завершение шага 3 плана готовности.

Скрипт отказывается повторно использовать каталог результатов и занятый serial.

Проверены API 36, 720×1280 px, density 320, fontScale по умолчанию, AGP 8.9.2, Kotlin 2.3.20, Buddy 0.3.0, KSP 2.3.6, JDK 21.0.2. Исходная ревизия шаблона до и после совпала. Пользовательская сессия, профиль плагина и Mealio не менялись.

Запуск требует заранее подготовленной минимальной копии `:app`, установленного API 36 Play Store x86_64 system image, Android SDK и JDK 21. Исходники стенда не включаются в runtime-пакет и не запускаются через обычный `npm test`:

```sh
node tests/android/geometry.mjs \
  --template /absolute/path/to/prepared-BridgeTest \
  --output /tmp/new-compose-geometry-verification \
  --sdk /absolute/path/to/Android/Sdk \
  --port 5586
```

`--output` должен отсутствовать. Проверка нативного переноса завершает процесс с ошибкой при неверных нативных размерах; сравнение с браузером отдельно записывается в `evidence.json` как `visualMatches` и `visualDifferences`. Успех нативных assertions при `visualMatches=false` не означает успешную визуальную приёмку.

## Измерения настоящего Android

Все числа в dp; ширина измерена по runtime bounds контейнера и дочернего Text, отступ — по разнице их координат. Это реальные значения, а не вычисление ожидаемого результата из JSON модели.

| Случай | До: внешний / внутренний размер | После первой правки | После второй правки |
|---|---|---|---|
| A: `width → height → padding` | 100×64 / 68×32 | 120×64 / 88×32 | 140×64 / 108×32 |
| B: `padding → width → height` | 132×64 / 100×32 | 152×64 / 120×32 | 172×64 / 140×32 |
| C: общий padding 16, затем переопределение осей | 100×64 / 68×32; H=16, V=16 | 100×64 / 84×32; H=8, V=16 | 100×64 / 84×64; H=8, V=0 |
| D: padding H=8, V=16, затем сброс H | 100×64 / 84×32 | 100×64 / 100×32; H=0, V=16 | 100×64 / 100×32; H=0, V=16 |

Высота контейнеров оставалась 64 dp; их позиции и расположение соседей в Android не изменились: верхние границы 16, 88, 160 и 232 dp. У A/B ширина менялась ровно на 20 dp в каждой итерации; неизменённый padding остался 16 dp. У C/D отступы заменяются, а не складываются. Все три debug-сборки и нативные assertions прошли в каждом запуске. Браузерные поля редактировались Playwright; Apply создавал снимок в тестовом режиме, подтверждение пользовательского baseline не выполнялось.

## Что блокирует визуальную приёмку

- Браузерная автоматическая компоновка теряет смысл порядка `padding → width/height`. Во второй итерации B имеет в браузере 140×32 dp, в Android — 172×64 dp. Это также сдвигает следующих соседей в браузере. Сохранение исходного порядка в Kotlin решает A5, но само по себе не согласовывает модель внешнего размера с HTML.
- `Text(Modifier.fillMaxSize())` внутри Box заполняет Android-область, а в браузере ширина ограничивается примерно 9–10 dp ширины буквы. У A во второй итерации Android Text имеет ширину 108 dp. Поведение grid и fill требует отдельного исправления; только сравнивать контейнер недостаточно.
- `background` после padding в Android закрашивает внутреннюю область; HTML-фон закрашивает также padding контейнера. Это видно на настоящих PNG A/C/D. Порядок оформления тоже должен быть отражён в браузерной модели; числовое совпадение внешних bounds его не подтверждает.

Завершать визуальную приёмку B2/B6 по этому прогону нельзя. Следующее исправление должно согласовать наружный размер, область содержимого и область заливки в importer/renderer/переносе, затем повторить этот стенд. Изменения callbacks, структура, ресурсные выражения, другой viewport и увеличенный fontScale этим конкретным прогоном не проверялись.
