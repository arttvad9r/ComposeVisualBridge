# Аналоги и возможности адаптации кода

Проверено 10 октября 2026 года. Область: ручное визуальное редактирование → структурированная передача → изменение исходников агентом, а также библиотеки редакторов и перетаскивания.

## Вывод

Похожие продукты уже есть, включая очень близкие по сценарию. Для нашей разработки разумнее переиспользовать отдельные механизмы, сохранив собственный документ с ID, sourceRevision и отправленным снимком. Полный форк веб-редактора не решает редактирование существующего Android Compose-экрана.

Первый кандидат для практической проверки — **современный @dnd-kit/dom**: работает без React и даёт готовые механизмы ввода. **Pragmatic Drag and Drop** полезен для правил вставки и дерева. **Design Mode** и **moldui** — наиболее близкие MIT-проекты для изучения передачи агенту. Для модели Compose полезен **ComposeFlow**, но его Kotlin-код не подключается к нашему JavaScript напрямую, а текст лицензии требует уточнения.

Это рекомендация по результатам чтения, а не утверждённая смена архитектуры. В рамках исследования сторонние инструменты не устанавливались, их код не выполнялся и не включался в продукт.

## Как проверялось

Рассмотрены 18 репозиториев. Проверены первичные README, LICENSE, дерево файлов и метаданные GitHub; исходники ключевых механизмов изучены выборочно. Commit SHA зафиксированы в [снимке источников](sources-2026-10-10.json). Ни количество звёзд, ни реклама ускорения агентов не использованы как доказательство качества.

Чтение исходников подтверждает наличие механизмов, но не доказывает их совместимость с нашим браузером. Проверка реальной работы и зависимости пакетов — следующий отдельный эксперимент. Метаданные pushed_at обозначают push в репозиторий, а не дату выпуска или гарантированную поддержку.

## Какие конкретно части можно адаптировать

Ссылки ниже закреплены за прочитанными коммитами. Оценки стоимости относительные, без обещания сроков.

### 1. Перетаскивание: dnd-kit + правила дерева

В [PointerSensor](https://github.com/clauderic/dnd-kit/blob/e522d9c6a3cbe39e6e980ee3b6fd7a78f238ab94/packages/dom/src/core/sensors/pointer/PointerSensor.ts) есть пороги начала drag, обработка разных способов ввода и интерактивных элементов. Это полезно для разделения клика, ввода текста и перемещения. [Пакет DOM](https://github.com/clauderic/dnd-kit/blob/e522d9c6a3cbe39e6e980ee3b6fd7a78f238ab94/packages/dom/package.json) имеет собственные зависимости: отсутствие React не означает отсутствие зависимостей.

В [tree-item](https://github.com/atlassian/pragmatic-drag-and-drop/blob/b1d41f1ab4fea58eef515145abee3c0cdd3cbfbd/packages/hitbox/src/tree-item.ts) явно разделены reorder-above, reorder-below, make-child, reparent и заблокированная операция. Это лучше, чем смешивать геометрию указателя и изменение дерева в одной функции. Есть [тесты правил](https://github.com/atlassian/pragmatic-drag-and-drop/blob/b1d41f1ab4fea58eef515145abee3c0cdd3cbfbd/packages/hitbox/__tests__/unit/tree-item.spec.ts).

**Адаптация:** ввод/геометрия → намерение перемещения → наша move() → наша History → сохранение. Сохранить запрет циклов и стабильные ID. Не ставить оба полных drag-движка одновременно: сравнить их в отдельном стенде; из второго при необходимости использовать только правила/идеи.

**Стоимость:** средняя. Нужна сборка выбранной npm-зависимости либо прозрачный перенос небольшой части с лицензией; нужно корректно освобождать обработчики при перерисовке.

### 2. Передача агенту: Design Mode

В [change-tracker](https://github.com/SandeepBaskaran/design-mode/blob/011ba9d3098d136ecc34488aa02d6c8e5a38877f/packages/extension/src/content/change-tracker.ts) различаются style/text/DOM-изменения, сохраняются исходное и конечное положение, viewport и статус. [feedback-session](https://github.com/SandeepBaskaran/design-mode/blob/011ba9d3098d136ecc34488aa02d6c8e5a38877f/packages/mcp-local/src/feedback-session.ts) содержит состояния ожидания/работы/остановки, cursor и ограниченное ожидание ответа.

**Адаптация:** маленький локальный протокол статуса передачи, понятный отчёт и чтение отправленного снимка. Наш baseline/current/applied остаётся основой; cursor не подменяет revision. Не переносить cloud relay, аналитику и Chrome storage API в локальный прототип по умолчанию.

**Стоимость:** средняя. Изолировать интерфейс транспорта; тестовый режим и разрешение на перенос остаются явными.

### 3. Отчёт о правках и будущий overlay: moldui

[buildSyncPrompt](https://github.com/Manavarya09/moldui/blob/18e00247c9a837b9140fe42df37bbd8cca3e945c/src/differ.js) формирует задание из типов изменений. [mapper](https://github.com/Manavarya09/moldui/blob/18e00247c9a837b9140fe42df37bbd8cca3e945c/src/mapper.js) ищет вероятные файлы по маршруту, классам, ID и тексту. Это эвристика; записанные в коде коэффициенты confidence не являются измеренной точностью. [editor](https://github.com/Manavarya09/moldui/blob/18e00247c9a837b9140fe42df37bbd8cca3e945c/src/inject/editor.js) использует обычный JS, направляющие и историю операций.

**Адаптация сейчас:** русский отчёт рядом с JSON: что изменено, где source, baseline/sourceRevision, что передано, что осталось черновиком. **Позже для веба:** отдельный overlay-адаптер. Proxy не нужен для нашего собственного макета.

**Стоимость:** низкая для отчёта, высокая для proxy/overlay. Прямой перенос серверного кода без проверки обработки путей и сетевых границ не рекомендован. Автоматическое headless-применение Claude не переносить в тестовый Apply.

### 4. Выбор элементов: React Grab

[primitives](https://github.com/aidenybai/react-grab/blob/ea4bbec9e80f4802e8ae19ad18431edb9ddbb670/packages/react-grab/src/primitives.ts) позволяет выбирать элемент с ограничением области и фильтром. Это пригодится для исключения панели/оверлеев и выбора вложенных целей.

**Адаптация:** изолированный picker для будущего веб-адаптера. Для текущих синтетических Compose-узлов надёжнее сохранять наши data-node-id и source. Нельзя получать React ancestry синтетического превью и выдавать его за источник Kotlin.

**Стоимость:** средняя; полная библиотека может быть избыточна ради одного hit-test.

### 5. Модель Compose: ComposeFlow

[TextTrait](https://github.com/ComposeFlow/ComposeFlow/blob/3347013354285e6103a9a693aff5f77b74e37912/core/model/src/commonMain/kotlin/io/composeflow/model/parameter/TextTrait.kt) объединяет сериализуемые параметры текста, описание редактируемых свойств и работу с Compose. В проекте есть отдельные modifier-модели и интерфейс [CodeGenerator](https://github.com/ComposeFlow/ComposeFlow/blob/3347013354285e6103a9a693aff5f77b74e37912/core/model/src/commonMain/kotlin/io/composeflow/model/CodeGenerator.kt).

**Адаптация прежде всего архитектурная:** единое описание компонента со свойствами, ограничениями, отображением и подсказкой переноса в Compose. Это позволит не дублировать знание типов в валидаторе, inspector и renderer. Генерацию целого нового проекта не путать с безопасной правкой существующего экрана.

**Стоимость:** низкая для собственного registry по этой идее; высокая для прямого переноса Kotlin-модулей/нативного renderer.

### 6. Альтернатива собственного inspector: Puck

[DragDropContext](https://github.com/puckeditor/puck/blob/d1644c3e73beb109436c1a4a1f6a5276304b9ad9/packages/core/components/DragDropContext/index.tsx) использует современный dnd-kit и дополнительные механизмы вложенных зон. Puck уже решает значительную часть интерфейса редактора.

**Адаптация:** отдельный эксперимент с компонентами Column/Row/Text/Button и конвертером нашего JSON. Source и sourceRevision нельзя потерять при сериализации. Принимать решение по стабильности вложенности, русским полям и сохранению diff, а не по красивому демо.

**Стоимость:** высокая для миграции, средняя для отдельного стенда. На текущем этапе это запасной вариант, а не рекомендация переписать frontend.

## Что изменилось в понимании проекта

1. Сценарий визуальной правки с передачей агенту уже существует; обещать уникальность идеи нельзя.
2. Наша особенность в исследованной выборке — отдельное промежуточное представление существующего Compose-экрана, явная исходная ревизия и сохранение согласованного снимка. Это не доказательство отсутствия других аналогов в мире.
3. Для веб-приложений редактирование живой страницы зачастую удобнее макета. Это отдельный будущий адаптер, а не причина отказаться от Compose-представления.
4. Надёжность drag и source mapping важнее добавления собственного чата/облака. Ни CSS selector, ни line number сами по себе не гарантируют правильный экземпляр после изменения кода.
5. Рамка свободного перемещения не снимает вопрос семантики: как результат станет Row/Column/Box без поломки адаптивности.

## Следующая дешёвая проверка

Предлагается отдельный стенд, без замены текущего редактора и пользовательской сессии:

- Сравнить @dnd-kit/dom и Pragmatic DnD на одном дереве: две вложенные Column, Row, Text, Button; scale, прокрутка, пустой контейнер, отмена, клавиатура.
- Каждый движок выдаёт только parentId/index; состояние меняют существующие move/History. Проверить точное восстановление JSON после Undo и отсутствие потерь source.
- Сравнить работу во встроенном браузере, объём зависимостей, сложность teardown и поддержки. Версии брать из реально выбранного релиза; SHA исследования не равен версии npm.
- Отдельно сделать пример русского отчёта по нашему applied на основании структуры отчётов MIT-проектов. Он не запускает перенос автоматически.
- Только после результатов выбрать библиотеку и обновить спецификацию/план. Вопрос полного перехода на Puck оставить запасным.

**Что не проверено:** запуск сторонних приложений, точность их source mapping, совместимость extension API со встроенным браузером, production-надёжность, условия всех transitive-зависимостей и полный цикл переноса в Android. Следующий эксперимент должен проверять именно эти применимые к выбранному решению части.
